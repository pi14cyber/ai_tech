**Факты за:**
  - Первыми ломаются неатомарные сценарии без сохранения промежуточного состояния (State Management) и распределённый перехват ошибок. ### Q1.4. Пределы масштабирования

**Факты за:**
  - Физический предел параллельной записи SQLite (Single-Writer Lock): локальная база данных обрабатывает 40 000+ запросов/сек на чтение (латентность < 2 мс) и 10 000–50 000 транзакций/сек последовательной записи, но при 10 параллельных пишущих потоках деградирует по времени выполнения в ~7 раз, а при 50 параллельных потоках — в 20,8 раза (с 6,8 сек у MySQL до 142 сек у SQLite), приводя к блокировкам SQLITE_BUSY (Tech-Insider Benchmark, 2026; LinkedIn / SQLite Stress Test, 2026; GitHub / sqlite-multiwriter, 12.10.2026).
  - Порог размера локальной базы для перехода на клиент-серверную СУБД (PostgreSQL): переход с локального файла на выделенную инфраструктуру становится обязательным при выходе размера данных за 1 ТБ либо при появлении конкурентных фоновых процессов записи на уровне нескольких серверов (Daily.dev Guide, 2026; Tinybird / Postgres vs SQLite).
  - Пределы монолитных репозиториев (Git Repo Size Thresholds): локальный Git без выделенной инфраструктуры (Git LFS, Scalar, геометрический repack) деградирует по скорости clone и fetch при размере репозитория > 1–5 ГБ; отдельные файлы > 100 МБ блокируются хостингами, а репозитории объёмом ~250 ГБ в Azure Repos упираются в лимит pack-файлов и блокируют операции записи (GitHub Blog / Git Database Internals; GitHub Discussions #188694, 08.03.2026; Microsoft Learn / Azure Repos Limits, 2026).
